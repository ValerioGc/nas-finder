# Development guide

This guide describes the implementation and maintenance of NAS Finder. For user
workflows, see the [README](README.md). For the wire protocol and NAS configuration,
see the [NAS integration guide](NAS-INTEGRATION.md).

## Technology and project boundaries

The frontend uses Vue 3, TypeScript, Vite, and SCSS. The native backend uses Rust and
Tauri 2. NAS Finder, the setup wizard, and the gateway remain independent projects:
they do not import each other's source code or share a Cargo workspace.

Rust 1.89 or later is required for the standard library's file-locking API. Node.js
must satisfy `package.json`; the release workflows use Node.js 24.

## Local development

```sh
pnpm install
pnpm run tauri:dev
```

CI installs JavaScript dependencies with `npm ci`. Local pnpm installs synchronize
`package-lock.json` through the postinstall hook. After changing dependencies,
commit both `pnpm-lock.yaml` and `package-lock.json`. Use `pnpm run lock:npm` to
synchronize the npm lockfile explicitly and `npm run lint:lock` to check it.

### Code conventions

Use Vue `<script setup lang="ts">`, alias-based imports, and shared SCSS tokens.
Compound CSS class names use underscores; translation keys use camelCase. Keep
blank lines between style rules. Use English for documentation, comments, test
fixtures, and tooling messages; localized interface text belongs in its language
catalog.

`npm run format` applies Prettier, the SFC spacing formatter, and ESLint fixes.
Rust code follows rustfmt and Clippy. The vendored GLib source is kept close to its
upstream distribution; its local change is documented in `PATCHES.md`.

### Generated files and exclusions

Build output, coverage, test reports, and local environment files are excluded by
`.gitignore`. Keep lockfiles, native icons, shared project instructions, and vendored
sources under version control. `.env.example` and `.env.*.example` are allowed as
configuration templates; real `.env` files and local AWS/Codex state stay untracked.

Tauri generates `backend/gen/schemas/` and `backend/permissions/autogenerated/`
during the native build. These files are not versioned; `backend/build.rs` and
`backend/capabilities/main.json` remain the authoritative definitions. The capability
file references the generated schema for editor validation after the first build.

Prettier checks maintained backend JSON and the GLib patch notes while excluding
generated files and upstream vendored sources. ESLint excludes build/test artifacts;
SonarQube explicitly excludes generated BDD code and Allure output from test analysis.

### Shared styles and assets

`src/styles/global.scss` exposes the SCSS tokens, mixins, and placeholders to
component styles. Shared global classes include `primary_button`,
`secondary_button`, `icon_button`, `error_message`, `body_copy`, `hint`,
`empty_state`, and `visually_hidden`. Scoped styles define component-specific
spacing and variants.

SVG action icons are imported with `?no-inline` and displayed through the shared
`icon` CSS mask. Accessible action names and tooltips use translated messages.
The application logo is `src/assets/logo.svg`; the configured native icon files
are `backend/icons/icon.png` and `backend/icons/icon.ico`.

PurgeCSS, selector consolidation, and cssnano run only in production builds.
Autoprefixer also runs in development.

## Native command API

| Command                | Arguments                           | Behavior                                                          |
| ---------------------- | ----------------------------------- | ----------------------------------------------------------------- |
| `list_saved`           | None                                | Load saved devices with their online state reset.                 |
| `discover_nas`         | `target` (string or null)           | Discover devices and merge them with the saved list.              |
| `save_nas`             | `id: string`                        | Save an online device from the latest discovery.                  |
| `forget_nas`           | `id: string`                        | Remove a device from the saved list.                              |
| `open_nas`             | `id: string`                        | Open a validated, online device using a backend-generated URL.    |
| `confirm_nas_endpoint` | `id: string`, `expectedUrl: string` | Confirm a changed saved connection and return the updated device. |

Native window commands provide minimize, maximize/restore, close, and window
movement. `build.rs` uses `AppManifest::commands` to generate permissions, which
are explicitly granted to the `main` window by `backend/capabilities/main.json`.

The backend accepts device identities rather than arbitrary paths or URLs for
opening pages. Endpoint confirmation receives the displayed URL only for an exact
comparison against the latest candidate. It also checks the current saved record,
so a stale confirmation or another instance's intervening change is rejected.

Errors cross IPC as codes: `invalid_address`, `network_unavailable`, `busy`,
`storage_unavailable`, `invalid_device`, `browser_unavailable`, and
`endpoint_changed`. The frontend maps them to localized messages.

## Operation and storage guarantees

Blocking network, file, and process work runs through `spawn_blocking`. An
in-process mutex prevents overlapping operations. A system file lock on
`devices.lock` covers each storage transaction across processes; a competing
instance receives `busy` rather than overwriting another transaction. The lock
file remains in place after the handle is released.

Saved records are stored in `devices.json` under Tauri's application configuration
directory. The backend:

- Reads at most 64 KiB plus one byte before rejecting an oversized file.
- Validates identities, hostnames, IPv4 addresses, ports, duplicates, and the
  maximum of 64 saved devices.
- Reports a corrupt file without silently replacing it with an empty list.
- Normalizes runtime fields and sorts persistent records by identity before
  comparison, avoiding writes when only online state or list order changes.
- Writes to a unique temporary file, synchronizes it, and atomically replaces the
  destination. On Unix, it also synchronizes the parent directory.

A failed storage read or lock acquisition during refresh invalidates the previous
online state in the backend. A changed saved address, port, or protocol is reported
through `previousEndpoint`. Its old record stays on disk until explicit
confirmation, and native opening and ordinary saving reject the changed candidate.

## Discovery behavior

Discovery listens for approximately three seconds and retransmits requests every
900 ms. Interface enumeration uses `ip` on Linux and PowerShell on Windows, with a
two-second process timeout and a 64 KiB output limit. A timed-out process is killed
and reaped; missing tools, failed enumeration, or a timeout fall back to global
broadcast and the saved device addresses.

Replies are limited to 512 bytes and 128 discovered identities. The source IPv4
address determines the connection address. Deduplication prefers the saved address
when it still responds, then the lowest address for a deterministic result. Manual
discovery adds the requested address to the saved addresses; it does not scan every
host in a subnet.

See [Discovery protocol](NAS-INTEGRATION.md#discovery-protocol) for packet fields,
identity derivation, and trust boundaries. IPv6 and explicit interface selection
are not implemented.

## Verification

### Frontend and build checks

| Command                     | Purpose                                                              |
| --------------------------- | -------------------------------------------------------------------- |
| `npm run format:check`      | Check formatting and SFC spacing.                                    |
| `npm run lint`              | Run ESLint and verify npm lockfile consistency.                      |
| `npm run type-check`        | Type-check the application, tests, and configuration.                |
| `npm run test:coverage`     | Run unit/component tests and enforce per-file coverage thresholds.   |
| `npm run test:e2e`          | Run Playwright BDD scenarios against the simulated native transport. |
| `npm run test:build`        | Build the frontend and check its production module graph.            |
| `npm run release:test:unit` | Exercise the release and lockfile scripts.                           |
| `npm run release:check`     | Check version alignment and the corresponding changelog entry.       |

Frontend coverage requires at least 80% per file for lines, statements, functions,
and branches. Reports are written under `coverage/`.

Playwright serves Vite on port 1421 and simulates IPC only in test fixtures. Install
its managed Chromium version with `npm run test:e2e:install` on first setup or after
a Playwright update. JavaScript dependency installation does not install Chromium.

### Rust and native checks

```sh
cargo fmt --manifest-path backend/Cargo.toml --check
cargo clippy --manifest-path backend/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path backend/Cargo.toml
cargo test --manifest-path backend/Cargo.toml --release --test glib_variant
npm run tauri -- build --debug --no-bundle
```

If sccache is unavailable, prefix a Cargo command with `RUSTC_WRAPPER=` rather than
changing global settings. `npm run coverage:rust` requires `cargo-llvm-cov` and
writes `backend/coverage/lcov.info`.

Rust tests cover local UDP sockets, malformed replies, nonce validation,
deduplication, bounded file reads, atomic replacement, cross-process locking,
process timeouts, and endpoint confirmation. Frontend IPC mocks do not exercise
the Rust backend. Physical broadcast discovery, Windows interface enumeration,
WebView behavior, and actual browser launching need separate desktop validation.

### Dependency security

The [audit workflow](.github/workflows/audit.yml) runs weekly and gates tagged
releases. It checks npm advisories at the high-severity threshold and runs
`cargo audit --deny unsound` against `backend/Cargo.lock`.

GLib 0.18.5 is vendored with the compatible backport for RUSTSEC-2024-0429. See the
[patch notes](backend/vendor/glib/PATCHES.md) and keep the release-mode regression
test when updating the GTK/Tauri dependency chain. The `proc-macro-error`
`unmaintained` advisory remains visible and should be reviewed during upstream
updates.

### SonarQube

The optional local SonarQube environment uses Podman:

```sh
npm run podman:sonar:up
npm run test:sonar
npm run podman:sonar:down
```

`test:sonar` requires `SONAR_TOKEN`, `cargo-llvm-cov`, and a running SonarQube
instance at `http://127.0.0.1:9000`. It generates JavaScript and Rust coverage,
exports Clippy findings, and runs SonarScanner. Project findings and quality gates
are available only after a completed analysis and with the appropriate access.

The scanner runs with `--userns=keep-id:uid=1000,gid=1000` to map the host user
to the image's scanner user. This allows rootless Podman to read owner-only files
such as `pnpm-workspace.yaml` and write analysis output in the mounted workspace.
An `EACCES` error for `/usr/src/…` indicates a filesystem access failure; check the
user mapping and file ownership before changing authentication settings.

## Release tooling

The release verifier requires matching versions in `package.json`, the npm
lockfile root, `backend/Cargo.toml`, and `backend/tauri.conf.json`, plus a matching
entry in `CHANGELOG.txt`. Correct a mismatch before preparing or tagging a release.

`npm run release:test` audits npm dependencies, formats the repository, runs
checks and tests, and builds desktop bundles. This command modifies formatted
files and creates build artifacts.

`npm run release:merge -- --dry-run` reports the proposed version and branches.
Without `--dry-run`, the merge script updates release metadata, runs preparation,
commits the changes, merges into the target branch, creates a tag, and pushes the
branch and tag. Use it only when intentionally publishing a release.

If no `v*` tag is reachable from the current branch, the script makes the first
release using the version already declared in `package.json`, without a version
bump. It uses the full commit history for a missing changelog section and creates
`v<current-version>` after preparation succeeds. Later releases keep the usual
patch, minor, or major bump behavior.

The [build workflow](.github/workflows/build.yml) verifies the tagged commit, runs
audit and frontend checks, builds Linux and Windows packages, and publishes release
notes and SHA-256 checksums. Keep the changelog filename and heading format because
the scripts consume them directly.
